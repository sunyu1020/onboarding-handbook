# 第 3 屏 v2 开发指令：JD 拆解 Agent

## 背景

第 3 屏 v1（岗位名 → 8 字段岗位地图 → 收藏）已完成并验收。v2 在第 3 屏内部新增「JD 拆解 Agent」模式，实现产品最核心的差异化能力：**把一份招聘 JD 翻译成"真实工作地图"，并支持追问对话**。

本指令依赖 `D:\workplace\prompt-JD拆解Agent.md` 定稿（含 3 个 Prompt，全部逐字复制进代码，禁止改写、增删任何字）。

## 一、交互架构：第 3 屏内部双 Tab

第 3 屏改成两个 tab（参照第 7 屏 open-tabs 的样式体系）：

- **Tab 1「岗位名拆解」（v1 原样保留）**：现有输入框 + 生成按钮 + 结果卡片 + 收藏逻辑，**一行代码不许改**。包括它的四个异常态（无 key/加载中/API 报错/JSON 解析失败）也原样保留。
- **Tab 2「JD 拆解 Agent」（v2 新增）**：
  1. **输入区**：大文本框（textarea，占位"粘贴一份招聘 JD 原文…"）+ 上传截图按钮（"上传 JD 截图"）
  2. 上传截图 → 调智谱 GLM-4V-Flash 提字 → **提取结果回显到同一个 textarea，用户可手动修正** → 点「拆解这份 JD」
  3. 拆解 → 结果卡片（8 字段 + 新增 jdDecoded 高亮板块）→ 收藏按钮（☆）
  4. 卡片下方自动展开**追问对话区**：预置 3 个快捷追问按钮 + 输入框 + 流式打字机输出

v2 生成的结果卡片点击收藏，写入 v1 同一 key `job_library`（AI 生成收藏，存完整数据），**收藏对象里必须含 jdDecoded 字段**（v1 收藏的旧数据没有此字段，渲染时用 `j.jdDecoded || []` 兼容）。

## 二、三个 Prompt 文件（防篡改机制，同 v1）

从 `prompt-JD拆解Agent.md` 逐字复制，存成三个文件，用 `?raw` 导入：

| 文件 | 来源 | 用途 |
|---|---|---|
| `src/prompt-jd-ocr.txt` | Prompt ①（截图提字） | 智谱 GLM-4V-Flash |
| `src/prompt-jd-agent.txt` | Prompt ②（首次拆解） | DeepSeek，System Prompt |
| `src/prompt-jd-chat.txt` | Prompt ③（追问对话） | DeepSeek，System Prompt |

导入方式与 v1 相同：`import xxx from './prompt-jd-agent.txt?raw'`。三个文件的内容 = 定稿里 ``` 代码块内的原文，一字不改，开头结尾都不要加多余字符。

## 三、截图提字（智谱 GLM-4V-Flash）

**端点**：`https://open.bigmodel.cn/api/paas/v4/chat/completions`
**鉴权**：`Authorization: Bearer ${import.meta.env.VITE_ZHIPU_API_KEY}`
**模型**：`glm-4v-flash`（免费）

**请求体**：
```js
{
  model: 'glm-4v-flash',
  messages: [{
    role: 'user',
    content: [
      { type: 'text', text: OCR_PROMPT },  // prompt-jd-ocr.txt 全文
      { type: 'image_url', image_url: { url: imageBase64 } }  // 带 data: 前缀的完整 data URL
    ]
  }]
}
```

**图片处理（必须做）**：
1. 用 `<input type="file" accept="image/*">` 选图
2. 读为 Image 对象 → 画到 canvas → **压缩到宽边 ≤ 1280px**（等比缩放）→ `canvas.toBlob(blob => ..., 'image/jpeg', 0.8)` → `FileReader` 读成 base64
3. 传给智谱的 base64 **必须带 `data:image/jpeg;base64,` 前缀**，否则 400
4. canvas 压缩是异步的（toBlob 回调），注意不要在 blob 出来前就发起请求

**回显要求（铁律）**：提字结果必须回显到 textarea **且可编辑**，用户修正后才允许点拆解。OCR 翻车用户能自救。

**失败处理**：
- 智谱 key 为空（`!import.meta.env.VITE_ZHIPU_API_KEY`）：上传截图按钮置灰，title 提示"需配置 VITE_ZHIPU_API_KEY"（参照 v1 无 key 态样式）
- 提字结果为空/明显不是 JD（返回内容过短或全是标点）：提示「没认出有效文字，请检查截图或直接粘贴 JD 文本」，不进入拆解
- 网络/鉴权错误：toast 或错误条显示原始错误信息，参照 v1 的 401/402/429 文案风格

## 四、首次拆解（DeepSeek）

- System Prompt = `prompt-jd-agent.txt` 全文
- User 消息模板（Prompt ② 底部已给）：`` `以下是用户提供的 JD 原文：\n${jdText}\n请按铁律拆解。JD 里的套话不要复述，读出它没写的部分。` ``
- **参数**：`temperature: 0.7`、`max_tokens: 2500`、`response_format: { type: 'json_object' }`（与 v1 同机制，v1 的 generate() 调用是现成范本）
- 加载态、错误态：沿用 v1 的四态处理（无 key/加载中/HTTP 错误码/JSON 解析失败）
- **JSON 解析失败兜底**：v1 的兜底逻辑直接复用；解析失败时提示"AI 输出格式异常，请重试"

**非 JD 输入引导（测试用例 4 的落地）**：如果 AI 返回的内容里 `jobName` 为空、或明确输出"这不是一份 JD"之类的话，则**不渲染卡片**，改为提示「这看起来不是一份招聘 JD，请粘贴真正的 JD 原文或重新上传截图」。判断逻辑：解析出的 jobName 为空 或 oneLineTruth 为空 → 走引导分支。

## 五、结果卡片渲染

8 字段渲染结构与 v1 相同（oneLineTruth 大字 + 可折叠模块卡片），**新增一个高亮板块 jdDecoded**，位置在 oneLineTruth 下方、dailyWork 上方：

- 板块标题：「JD 没写的大实话」（或类似）
- 每条渲染为一行：**JD 原文部分**（加引号、次要色、可加删除线或引用样式）→ 箭头 → **翻译部分**（主色、正常字重）
- 示例渲染效果：`"JD 写「参与客户需求调研」 → 实际是「你拿着问题清单一坐两小时地访谈，需求藏在客户抱怨的第三句话之后」"`
- 无 jdDecoded 字段时该板块不渲染（兼容 v1 旧收藏）

## 六、追问对话（DeepSeek，流式）

**生成卡片成功后**，卡片下方自动展开对话区（如果已有旧对话内容，先清空）：

**系统消息** = `prompt-jd-chat.txt` 全文，但其中 `{上一步生成的 JSON}` 占位符要**替换为本次拆解结果的 JSON 字符串**（对象原样 JSON.stringify）。

**请求**：
- `temperature: 0.5`、`stream: true`
- messages 数组：`[{role:'system', content: 替换占位符后的Prompt③}, ...历史对话, {role:'user', content: 新问题}]`（历史对话保留在内存数组里，**不落 localStorage**，刷新页面清空）

**流式解析（SSE）**：
- 用 `fetch` + `response.body.getReader()` 读流
- 按行切分，剥掉 `data: ` 前缀，跳过空行和注释行
- `[DONE]` 行 = 结束
- 每行 JSON.parse 后取 `choices[0].delta.content`，追加到回答区（打字机效果）
- 注意 DeepSeek 流里**首个 chunk 可能是 role 而非 content**（delta.content 为 undefined），要容忍，不能抛错

**交互细节**：
- 回答期间：发送按钮禁用 + 显示"回答中…"，结束后恢复
- 回答区高度有限制（max-height + 滚动），新内容自动滚到底部
- 3 个快捷追问按钮（点击即发送，按钮文案即问题）：
  - 「这个岗位面试会问什么」
  - 「第一个月最重要的是什么」
  - 「这份 JD 有哪些坑」
- 用户也可自由输入问题
- 回答内容**不允许用 markdown 标题**（Prompt ③ 已要求短段落+数字列表，前端渲染时把 `1. ` `2. ` 转成换行+缩进即可，不要引入 markdown 渲染库）
